# better-auth-server

Backend API built with [Hono](https://hono.dev), [BetterAuth](https://www.better-auth.com), and [Drizzle ORM](https://orm.drizzle.team), using PostgreSQL.

It exposes:
- auth endpoints under `/api/auth/*` (handled by BetterAuth + plugins)
- custom admin endpoints under `/api/admin/*` (RBAC, users, roles, permissions)
- health check endpoint at `/health`

## Technical stack

- Runtime: Bun
- HTTP framework: Hono
- Auth framework: BetterAuth
- ORM: Drizzle ORM
- DB: PostgreSQL
- Request validation: Valibot (`@hono/standard-validator`)

## What the backend does

- Handles authentication with:
  - email/password + email verification
  - Google and Discord OAuth
  - passkeys (WebAuthn)
  - magic links
  - 2FA (TOTP + backup codes)
  - JWT with JWKS
- Handles authorization at two levels:
  - `user.role` (BetterAuth user field, used by admin middleware)
  - custom RBAC tables (`role`, `permission`, `user_role`, `role_permission`)
- Enriches session/JWT user payload with RBAC roles and permissions.

## High-level architecture

1. `src/index.ts` initializes Hono and CORS on `/api/*`.
2. `/api/auth/*` is routed directly to `auth.handler(...)`.
3. `/api/admin/*` uses middleware:
   - `requireSession`: valid session required
   - `requireRole("admin")`: admin role required
4. Admin services use Drizzle for CRUD operations on users/roles/permissions.

## Prerequisites

- Bun (recommended >= 1.3.x)
- PostgreSQL
- Environment variables configured (`.env`)

## `.env` configuration

Start from `.env.example`, but note: the code reads `AUTH_SECRET` (not `BETTER_AUTH_SECRET`).

Minimal working example:

```env
AUTH_SECRET=your_secret_key_here
BETTER_AUTH_URL=http://localhost:3000
DATABASE_URL=postgres://app:app@localhost:5432/betterauth
TRUSTED_ORIGIN=http://localhost:4200

RP_ID=localhost
RP_NAME=BetterAuth Demo App
APP_NAME=BetterAuth Demo

GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
DISCORD_CLIENT_ID=
DISCORD_CLIENT_SECRET=
```

Variables used by the code:

- `AUTH_SECRET`: BetterAuth secret
- `BETTER_AUTH_URL`: backend base URL
- `DATABASE_URL`: PostgreSQL connection string
- `TRUSTED_ORIGIN`: allowed frontend origin (CORS/trusted origin)
- `APP_NAME`: auth app name
- `RP_ID`, `RP_NAME`: passkey/WebAuthn settings
- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`: Google OAuth
- `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`: Discord OAuth

Email settings:
- `src/utils/email.utils.ts` sends emails via SMTP using `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, and `MAIL_FROM`.
- Email HTML is generated by `src/utils/email-template.ts`.

## Database and migrations

Schema files:
- `src/db/schema/auth-schema.ts` (BetterAuth tables)
- `src/db/schema/rbac-schema.ts` (custom roles/permissions)

SQL migrations are in `drizzle/`.

`run-migrations.ts` uses a PostgreSQL advisory lock (`pg_advisory_lock`) to avoid race conditions on concurrent startup.

## Authentication (`/api/auth/*`)

Auth endpoints are provided by BetterAuth and mounted as:
- `GET/POST /api/auth/*`

Enabled plugins:
- Admin plugin
- JWT plugin (JWKS path `/.well-known/jwks.json`, JWT expiration `3m`)
- Magic link (`expiresIn: 300s`)
- Two-factor (TOTP + backup codes)
- Passkey (WebAuthn)

Custom session behavior:
- `auth.ts` adds to `session.user`:
  - `roles: string[]`
  - `permissions: string[]`
- values are loaded from RBAC tables (`user_role`, `role_permission`).

## Custom admin APIs (`/api/admin/*`)

All endpoints:
- require a valid session
- require admin role (`requireRole("admin")`)
- accept/return JSON

### 1) Users

#### `GET /api/admin/user`

Lists users (query is forwarded to `auth.api.listUsers`).

Response:
- BetterAuth payload enriched with:
  - `users[].roles` (RBAC role objects)
  - `users[].permissions` (deduplicated RBAC permission objects)

Status codes:
- `200` OK
- `401` Unauthorized
- `403` Forbidden
- `500` Internal Server Error

#### `POST /api/admin/user`

Creates a user via BetterAuth and RBAC associations (`user_role`).

Body:

```json
{
  "name": "Mario Rossi",
  "email": "mario@example.com",
  "password": "S3cure!Pass",
  "emailVerified": false,
  "image": "https://example.com/avatar.png",
  "role": "admin",
  "roleIds": [1, 2]
}
```

Main validations:
- valid `email`
- password min 8 chars, uppercase, lowercase, number, special char
- `role`: `"user"` or `"admin"` (array also allowed)
- `roleIds`: numbers, default `[]`

Response:
- `200`: `{ "userId": "<id>" }`
- `400`: role does not exist / validation error
- `500`: internal error

#### `PUT /api/admin/user/:userId`

Updates a user (partial update; password is not accepted).

Body: same fields as create, but optional (without `password`).

Current RBAC role behavior:
- existing `user_role` rows are deleted first
- if `roleIds` is present and non-empty: inserts the new associations
- if `roleIds` is `[]`: user remains with no RBAC roles
- if `roleIds` is omitted: **in the current implementation** associations are still removed

Response:
- `200`: `{ "userId": "<id>" }`
- `404`: user not found
- `400`: role does not exist / validation error
- `500`: internal error

### 2) Roles

#### `GET /api/admin/role`

Returns all roles.

Response:
- `200`: `RoleDto[]`

#### `GET /api/admin/role/permissions`

Returns roles with their permissions.

Response:
- `200`: `RoleDto[]` with `permissions`

#### `POST /api/admin/role`

Body:

```json
{
  "name": "manager",
  "description": "Manager role",
  "permissionIds": [1, 2]
}
```

Response:
- `200`: `{ "id": <roleId> }`
- `400`: role already exists / permission does not exist / validation error
- `500`: role creation error

#### `PUT /api/admin/role/:roleId`

Updates a role and replaces the `role_permission` mapping.

Body is the same as create role.

Response:
- `200`: `{ "id": <roleId> }`
- `404`: role not found
- `400`: permission does not exist / validation error
- `500`: update error

#### `DELETE /api/admin/role/:roleId`

Deletes a role.

Response:
- `200`: `{}`
- `404`: role not found

### 3) Permissions

#### `GET /api/admin/permission`

Lists permissions.

Response:
- `200`: `PermissionDto[]`

#### `POST /api/admin/permission`

Body:

```json
{
  "code": "user.read",
  "name": "Read users",
  "description": "Allows user read access"
}
```

Response:
- `200`: `{ "id": <permissionId> }`
- `400`: duplicate (`code`/`name`) or validation error
- `500`: creation error

#### `PUT /api/admin/permission/:permissionId`

Updates a permission.

Response:
- `200`: `{ "id": <permissionId> }`
- `404`: permission not found
- `500`: update error

#### `DELETE /api/admin/permission/:permissionId`

Deletes a permission.

Response:
- `200`: `{}`
- `404`: permission not found

## Important operational notes

- CORS is applied to `/api/*` with `origin = TRUSTED_ORIGIN` and `credentials: true`.
- Admin endpoints require a valid BetterAuth session/cookie.
- Initial bootstrap requires at least one user with `user.role = "admin"` (in the `user` table) to access admin APIs.
- Emails are sent via SMTP; configure `SMTP_*` and `MAIL_FROM` correctly.

## Bootstrap the first admin user

If you deploy the backend on a new environment, create a normal user first (sign-up flow), then promote it to admin with a DB update.

SQL:

```sql
UPDATE "user"
SET role = 'admin'
WHERE email = 'admin@example.com';
```

Optional (if needed for protected flows):

```sql
UPDATE "user"
SET email_verified = true
WHERE email = 'admin@example.com';
```

CLI example:

```bash
psql "$DATABASE_URL" -c "UPDATE \"user\" SET role='admin' WHERE email='admin@example.com';"
```
